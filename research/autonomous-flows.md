## Overview

**The question.** What do the autonomous flows in the sources do step by step, and what would an autonomous flow that runs beside the fork's baseline look like for this owner.

**The short answer.**

1. **Only one family is different in kind from the baseline: the loop driven by a checkable finish condition.** pstack's Autonomous run, davidondrej's `goal-loop` and Anthropic's `ralph-loop` have no spec and no tickets. They have one objective, one command that proves progress, and a rule for when to stop. pstack's `figure-it-out` is the same loop with a framing step in front, and it is the closest thing in any source to the owner's phrase "building big with less up-front planning".
2. **The rest are the baseline chain with the human stops taken out.** `lfg` is plan, build, review and ship with a router in front. `/build auto` is `implement` in a loop after one approval. SDD is `implement-spec` run one task at a time, with the questions replaced by recorded decisions. `autoplan` is plan review with the user's answers supplied by six principles. Autopilot-full, Autopilot-stack and Orchestrate are the same build-and-verify loop at fleet scale.
3. **Both harnesses the owner uses now ship the loop itself.** Claude Code and Codex each have a `/goal` command, and Claude Code's is judged by a separate small model after every turn, where `ralph-loop` trusts a string the working model prints. So the collection does not need loop machinery. What the harness does not supply is the contract (objective, constraints, validation command, stop condition), and the `delegating` skill already holds that shape.
4. **The sources agree on the stop rule and disagree on external actions.** Five sources state the same rule the `delegating` skill adopted: do reversible work and report it, stop for irreversible actions. pstack contradicts itself on whether a ticket update or a chat message needs asking (A1), and `lfg` pushes and opens a PR without stopping, which the owner's own commit and push rule forbids.
5. **What stops a loop from running away is thin everywhere.** No source states a token or cost budget for a run. The bounds that exist are counts: five fix rounds per task in SDD, three CI fix rounds in `lfg`, two retries per unit in Orchestrate, an iteration cap in `ralph-loop` that defaults to unlimited.
6. **On model tiers, the usable guidance is in superpowers; on dispatch to another harness, T3 Code already does what the sources build by hand.** See D1 to D3.

**Counts.** 19 entries: 13 flows (A1 to A13, seven of them from pstack), 3 entries on tiers, caps and dispatch (D1 to D3), and 3 candidate shapes (S1 to S3). Of the 13 flows, none is proposed for adoption as it stands, 6 are proposed as sources of wording for a flow written here, and 7 are proposed rejected as flows.

### Which are different in kind

*Inference throughout; no source compares itself with the fork.*

- **Different in kind.** A2, A11 and A12 replace the chain with one objective and one check. They suit work whose "done" a command can prove (a migration, a coverage lift, a green build) and they are poor at anything that needs a design decision, which all three sources say themselves. A3 adds a framing step, a verification harness built before the work, and verdicts with three values, and so reaches further into unclear work than the other three.
- **The same chain, stops removed.** A9, A10 and A13 execute a plan the baseline would also have produced. What they add over `implement-spec` is a written rule for what to do at a decision point, and that rule is already in `delegating`.
- **The same chain at a scale the owner does not have.** A5, A6 and A7 assume cloud agents, stacked PRs and a merge queue.
- **A planning stage, not a flow.** A8 ends at an approved plan and builds nothing.
- **A primitive.** A4 is a fan-out with a selection rule, used inside the others.

### How a flow here would sit on what is decided

- **`delegating` and its unattended rule.** The rule (take the reversible default, list each such choice in the final report and on the ticket, stop on anything irreversible or on a premise that proves false) is the same rule A1, A9 and A10 state. Two details from the sources would sharpen it and are offered in A10: a ruling records what it costs if wrong, and the final report's list is exhaustive.
- **The tracker as the state that survives compaction.** Every flow that runs long keeps a file for this: SDD's ledger, pstack's store and `decisions.tsv`, `ralph-loop`'s state file, Addy's `tasks/todo.md`. SDD's reason is the strongest evidence for the idea in any source: controllers that lost their place after compaction "have re-dispatched entire completed task sequences" ([`skills/subagent-driven-development/SKILL.md` L131-L134](https://github.com/obra/superpowers/blob/8ca22dba9a94f28898bbce59f2537ff4d87c747d/skills/subagent-driven-development/SKILL.md?plain=1#L131-L134)). The planning theme already ruled that the tracker is that file here, with no run-trail script and no second ledger. A loop with no ticket (S1) has no such state unless it is given one, which is a reason to start it from a ticket.
- **The guard.** The catastrophic-only command guard is a backstop, not a permission model. An unattended run also needs the harness to stop prompting, and each harness does that differently: Claude Code's auto mode approves tool calls and `/goal` removes the per-turn stop; on Codex "an action that needs new approval fails" in a run that cannot ask, per its docs. Which permission mode a flow needs is a project fact, not a skill's behaviour. *Inference:* it belongs in project configuration beside "what needs approval".
- **Expensive workflows are user-invoked and never started by the agent.** Every flow here is started by a typed command, and `lfg`'s own description limits it to when "the user explicitly asks for autonomous end-to-end work" ([`skills/lfg/SKILL.md` L3](https://github.com/EveryInc/compound-engineering-plugin/blob/51aa537383744736eb8ad30468d34420e9fb8ea8/skills/lfg/SKILL.md?plain=1#L3)). Two things need care. `goal-loop` is model-invoked as published and may set a goal through a tool. And a typed `/goal` on the harness is not a skill, so the #15 rule holds only if the collection's skill drafts the contract and hands back the line to type, as the core guide does.
- **Commit and push only when asked.** `lfg` and the Autopilots end with pushed branches and PRs. A flow here would have to end earlier or read a grant from project configuration.

### Open questions for the theme session

1. **Is the loop worth a skill at all,** when `/goal` exists on both main harnesses and `delegating` already holds the contract? S1 is the cheapest way to find out.
2. **May an unattended run write to the tracker without asking?** pstack says yes and no (A1). The `delegating` rule already requires writing choices to the ticket, so the answer is presumably yes for the run's own ticket; the session should say so.
3. **Where does a run end?** A local branch, a pushed branch, or a draft PR. This decides whether "approvals" in project configuration needs a field for it.
4. **Does a per-ticket fix cap belong in `implement-spec`,** or only in an unattended flow? SDD's five rounds and breaker are the only worked answer.
5. **Tiers and dispatch.** D1 to D3 propose three or four sentences for `delegating` and nothing else. Whether more is wanted is the "rule pack" question the map parks.
6. **Is `freeze` wanted as scope control for a run?** No source read here uses a path lock; they all rely on the brief's scope line and on worktrees.

## The flows

### A1. pstack's autonomy policy, and where it contradicts itself

- **What it is.** Two texts set what a pstack agent may do without asking. The router's Autonomy section says "Reversible work and external actions (team chat, ticket updates, kicking off evals) proceed without asking." and pauses only "for irreversible writes: force-push to shared branches, deploys, data deletion, customer messages." ([`skills/poteto-mode/SKILL.md` L83-L85](https://github.com/cursor/plugins/blob/ccb5507cec1546dc88135c1139c811e6c59115ba/pstack/skills/poteto-mode/SKILL.md?plain=1#L83-L85)). Phrases such as going to bed or run until done are "Session overrides" that mean keep going ([`skills/poteto-mode/SKILL.md` L87](https://github.com/cursor/plugins/blob/ccb5507cec1546dc88135c1139c811e6c59115ba/pstack/skills/poteto-mode/SKILL.md?plain=1#L87)). The principle file lists "send external messages" among the actions that "still require confirmation" ([`skills/principle-never-block-on-the-human/SKILL.md` L18](https://github.com/cursor/plugins/blob/ccb5507cec1546dc88135c1139c811e6c59115ba/pstack/skills/principle-never-block-on-the-human/SKILL.md?plain=1#L18)), and gives the reasoning both rest on: "Since code changes are reversible and reviewable, a wrong decision usually costs less than blocking." ([`skills/principle-never-block-on-the-human/SKILL.md` L11](https://github.com/cursor/plugins/blob/ccb5507cec1546dc88135c1139c811e6c59115ba/pstack/skills/principle-never-block-on-the-human/SKILL.md?plain=1#L11)). A third text covers a standing grant: "Under a full-autonomy grant, decide a call that the grant covers, act on it, and report it, with no reply word and no offer." For a call only the operator can make, the agent applies a default and explains it; gates the operator named and the Always-pause list still hold ([`skills/poteto-mode/SKILL.md` L20](https://github.com/cursor/plugins/blob/ccb5507cec1546dc88135c1139c811e6c59115ba/pstack/skills/poteto-mode/SKILL.md?plain=1#L20)).
- **Kind**: convention doc.
- **Run profile.** Not a flow. It is the policy every pstack flow below inherits.
- **Proposed address**: none as text. The decision belongs in `delegating`'s unattended rule.
- **Why it could fit.** The contradiction is narrow and worth settling once: is a message to a team chat reversible. The router says it proceeds; the principle says it needs confirmation; the router's own pause list names only "customer messages". The grant text adds one useful distinction the `delegating` rule lacks: a call the grant covers is decided and reported, while a call only the owner can make gets a default plus a plain statement of what the owner could say to change it.
- **Why it might not.** The policy is written for a team where a ticket update or a chat post is routine. For a solo owner the only external surfaces are the tracker and the remote, and the owner's rule for the remote is already stricter than either text.
- **Copy / adapt / idea-only**: idea-only. Neither text can be copied because they disagree, and both name Cursor tools.
- **Overlap**: `delegating` unattended rule ([planning theme](https://github.com/Hissal/skill-collection/issues/35)); [workflow chains](workflow-chains.md) P13; [pstack ledger](ledgers/pstack.md) open question 4.
- **Idle context cost**: none.
- **Recommendation (proposed)**: have the theme session state one line for this collection: an unattended run may write to its own ticket and its own branch, and to nothing else outside the working tree, unless project configuration grants more.

### A2. pstack Autonomous run

- **What it is.** A thirteen-line playbook for one task driven to a finish condition: "You own the exit condition. Define done, then drive to it without stopping." ([`skills/poteto-mode/playbooks/autonomous-run.md` L3](https://github.com/cursor/plugins/blob/ccb5507cec1546dc88135c1139c811e6c59115ba/pstack/skills/poteto-mode/playbooks/autonomous-run.md?plain=1#L3)). The steps: state the exit condition as a checkable predicate before the first iteration; pick a wake mechanism with Cursor's `/loop`; make the smallest change the evidence justifies, check it against the predicate, commit if it advanced and discard it if not; log one row per iteration ([`skills/poteto-mode/playbooks/autonomous-run.md` L5-L10](https://github.com/cursor/plugins/blob/ccb5507cec1546dc88135c1139c811e6c59115ba/pstack/skills/poteto-mode/playbooks/autonomous-run.md?plain=1#L5-L10)).
- **Kind**: convention doc (playbook).
- **Run profile.** *Human:* gives the goal, the finish condition, the permissions and an escape hatch; the guide's example is four lines ([`docs/guide/07-overnight.md` L20-L27](https://github.com/cursor/plugins/blob/ccb5507cec1546dc88135c1139c811e6c59115ba/pstack/docs/guide/07-overnight.md?plain=1#L20-L27)). *Agent alone:* everything reversible, including fixes to things it trips over mid-run: "Do not park reversible work for the human or use `AskQuestion`. Surface only irreversible actions, genuine product or preference calls no experiment can settle, or a real dead end." ([`skills/poteto-mode/playbooks/autonomous-run.md` L9](https://github.com/cursor/plugins/blob/ccb5507cec1546dc88135c1139c811e6c59115ba/pstack/skills/poteto-mode/playbooks/autonomous-run.md?plain=1#L9)). *Stops:* the predicate, or a dead end. It may not stop early: "A plateau is not a stop", and it must "never relax the predicate to declare victory" ([`skills/poteto-mode/playbooks/autonomous-run.md` L11](https://github.com/cursor/plugins/blob/ccb5507cec1546dc88135c1139c811e6c59115ba/pstack/skills/poteto-mode/playbooks/autonomous-run.md?plain=1#L11)). *Cost:* one session and one watcher subagent. No iteration, time or token bound is stated; the guide's only brake is the escape hatch the human writes. *Needs:* a loop command, a decision log, a worktree.
- **Proposed address**: idea into S1.
- **Why it could fit.** It is the smallest complete description of the loop, and its two refusals (no relaxed predicate, no speculative changes left in) are the rules a loop most needs. The guide adds the precondition that matters for a first test: "Make the loop autonomous only after all four hold." The four are that the task has been done once by hand or watched, the agent has the same tools and signals the owner would use, every stage can stop the line, and repeated failures have been turned into checks ([`docs/guide/07-overnight.md` L11-L16](https://github.com/cursor/plugins/blob/ccb5507cec1546dc88135c1139c811e6c59115ba/pstack/docs/guide/07-overnight.md?plain=1#L11-L16)). It also names the commonest mistake: "a duration is not a finish condition" ([`docs/guide/07-overnight.md` L118](https://github.com/cursor/plugins/blob/ccb5507cec1546dc88135c1139c811e6c59115ba/pstack/docs/guide/07-overnight.md?plain=1#L118)).
- **Why it might not.** A plateau that is never a stop, with no bound, is how a loop burns a night. Step 4 lets the run open side PRs for anything it finds, which widens scope without the owner. The guide routes any run the user will review later through `figure-it-out` anyway ([`docs/guide/07-overnight.md` L38](https://github.com/cursor/plugins/blob/ccb5507cec1546dc88135c1139c811e6c59115ba/pstack/docs/guide/07-overnight.md?plain=1#L38)).
- **Copy / adapt / idea-only**: adapt four sentences. The rest names Cursor's `/loop` and pstack skills.
- **Overlap**: A11, A12; the harness `/goal`; fork `loop-me` (parked; it designs recurring workflows and is not this); [pstack ledger](ledgers/pstack.md) entry 35.
- **Idle context cost**: none.
- **Recommendation (proposed)**: take the predicate rule, the discard rule and the four preconditions into S1, and add the bound the source lacks.

### A3. pstack `figure-it-out`

- **What it is.** A skill for work no playbook fits, and for anything the user steps away from: "The deliverable before any code is the workflow itself" ([`skills/figure-it-out/SKILL.md` L9](https://github.com/cursor/plugins/blob/ccb5507cec1546dc88135c1139c811e6c59115ba/pstack/skills/figure-it-out/SKILL.md?plain=1#L9)). Five phases. Frame: a falsifiable definition of done, a quantified scope, and a rigor level. Design: units ordered riskiest unknown first, and "Build the verification harness before the work", with a baseline captured from the unchanged state ([`skills/figure-it-out/SKILL.md` L27-L32](https://github.com/cursor/plugins/blob/ccb5507cec1546dc88135c1139c811e6c59115ba/pstack/skills/figure-it-out/SKILL.md?plain=1#L27-L32)). Loop: each unit is an experiment that is kept or reverted, checked on the artifact and never on a self-report, with a verdict of verified, not verified or inconclusive: "Inconclusive is not a pass." - **What it is.** The controller loop for a written plan: a fresh implementer subagent per task, one reviewer per task that returns two verdicts (spec compliance and quality), a bounded fix loop, one whole-branch review at the end and one fix wave. State is a git-ignored ledger file that the controller trusts over its memory.
- **Kind**: skill plus three bash scripts and three prompt templates.
- **Run profile.** *Human:* approves the saved plan and picks the executor beforehand (stated in the release notes; the planning skills were not read). During the run, nothing: "Do not pause to check in with your human partner between tasks." ([`skills/subagent-driven-development/SKILL.md` L17](https://github.com/obra/superpowers/blob/8ca22dba9a94f28898bbce59f2537ff4d87c747d/skills/subagent-driven-development/SKILL.md?plain=1#L17)). At the end reads a list headed Rulings I made. *Agent alone:* conflicts, ambiguities and plan defects. Each is recorded as a ruling with three parts: what was decided, why, and what it costs if wrong ([`skills/subagent-driven-development/SKILL.md` L19-L25](https://github.com/obra/superpowers/blob/8ca22dba9a94f28898bbce59f2537ff4d87c747d/skills/subagent-driven-development/SKILL.md?plain=1#L19-L25)). The reasoning: "A wrong ruling costs rework your human partner can see and undo; a session parked on a question costs their whole day and buys nothing." ([`skills/subagent-driven-development/SKILL.md` L19-L25](https://github.com/obra/superpowers/blob/8ca22dba9a94f28898bbce59f2537ff4d87c747d/skills/subagent-driven-development/SKILL.md?plain=1#L19-L25)). *Stops:* "Four things stop you, and only these: an irreversible or destructive operation; a security-sensitive action; a side effect outside this worktree that norms say you ask about first (a merge, a push to a shared branch, a publish); and a plan so broken that every path forward is a guess." ([`skills/subagent-driven-development/SKILL.md` L27-L31](https://github.com/obra/superpowers/blob/8ca22dba9a94f28898bbce59f2537ff4d87c747d/skills/subagent-driven-development/SKILL.md?plain=1#L27-L31)). The fix loop is "Five rounds maximum per task" ([`skills/subagent-driven-development/SKILL.md` L372-L373](https://github.com/obra/superpowers/blob/8ca22dba9a94f28898bbce59f2537ff4d87c747d/skills/subagent-driven-development/SKILL.md?plain=1#L372-L373)): rounds one to three resume the implementer, rounds four and five bring a fresh one on a stronger model, and at the cap the controller adjudicates each open finding and parks it with a ruling. After the final review, "There is no second fix wave" ([`skills/subagent-driven-development/SKILL.md` L465-L469](https://github.com/obra/superpowers/blob/8ca22dba9a94f28898bbce59f2537ff4d87c747d/skills/subagent-driven-development/SKILL.md?plain=1#L465-L469)). *Cost:* two fresh contexts per task at least, up to ten more dispatches in a worst-case fix loop (inference from the round rules), and three at the end. About 12k tokens to load ([superpowers ledger](ledgers/superpowers.md) entry 5). The source gives relative figures only; see D1. *Needs:* a subagent tool that takes a model per dispatch, git worktrees, bash for the scripts, and a plan file in superpowers' own format.
- **Proposed address**: idea into S2.
- **Why it could fit.** It is the same job as `implement-spec` with the questions replaced by a written policy, and that policy is the most developed in any source. The release notes say why it was written: "One donated session had sat blocked for almost nine hours on a question the controller could have decided." ([`RELEASE-NOTES.md` L92](https://github.com/obra/superpowers/blob/8ca22dba9a94f28898bbce59f2537ff4d87c747d/RELEASE-NOTES.md?plain=1#L92)). Four parts are missing from `implement-spec` and from `delegating` as decided: the cost-if-wrong field on a ruling; the exhaustive final list, with its reason, "A ruling that dies with the workspace was a decision made in secret." ([`skills/subagent-driven-development/SKILL.md` L473-L480](https://github.com/obra/superpowers/blob/8ca22dba9a94f28898bbce59f2537ff4d87c747d/skills/subagent-driven-development/SKILL.md?plain=1#L473-L480)); a cap on fix rounds with a defined act at the cap; and the rule that the controller stays out of the code: "Never fix findings yourself in the controller session" ([`skills/subagent-driven-development/SKILL.md` L408-L409](https://github.com/obra/superpowers/blob/8ca22dba9a94f28898bbce59f2537ff4d87c747d/skills/subagent-driven-development/SKILL.md?plain=1#L408-L409)).
- **Why it might not.** It runs one implementer at a time: "Never dispatch multiple implementation subagents in parallel (conflicts)." ([`skills/subagent-driven-development/SKILL.md` L282](https://github.com/obra/superpowers/blob/8ca22dba9a94f28898bbce59f2537ff4d87c747d/skills/subagent-driven-development/SKILL.md?plain=1#L282)), where `implement-spec` runs a parallel frontier in worktrees. A reviewer per task is a cost the fork does not pay; it reviews once at the end. The ledger is the second state file the planning theme ruled out. The controller's authority to rule on plan defects is broad, and the owner should accept it knowingly.
- **Copy / adapt / idea-only**: idea-only for the skill. The ruling form and the four stop classes adapt as wording.
- **Overlap**: fork `implement-spec`; `delegating` (its unattended rule already cites "Rulings I made"); [superpowers ledger](ledgers/superpowers.md) entries 5 to 7; A9; A13.
- **Idle context cost**: none.
- **Recommendation (proposed)**: the main source for S2. A standout.

### A11. Anthropic `ralph-loop`

- **What it is.** A Claude Code plugin whose Stop hook refuses to let the session end and feeds the same prompt back, until the last assistant message contains a promise tag with the agreed text or an iteration cap is reached. State is one file in the project's `.claude` folder; without it the hook does nothing ([`plugins/ralph-loop/hooks/stop-hook.sh` L13-L18](https://github.com/anthropics/claude-plugins-official/blob/b8e53f1c05dff3b6d751297f6527990ffc81c2f4/plugins/ralph-loop/hooks/stop-hook.sh?plain=1#L13-L18)).
- **Kind**: hook plus three commands.
- **Run profile.** *Human:* writes one prompt and the flags, then walks away. The README puts the burden on the prompt: clear completion criteria, phases, a self-correcting test loop. *Agent alone:* everything, including when to claim completion; the only rule is not to lie: "Do not output false promises to escape the loop, even if you think you're stuck or should exit for other reasons." ([`plugins/ralph-loop/commands/ralph-loop.md` L18](https://github.com/anthropics/claude-plugins-official/blob/b8e53f1c05dff3b6d751297f6527990ffc81c2f4/plugins/ralph-loop/commands/ralph-loop.md?plain=1#L18)). *Stops:* the promise string, matched exactly, or the cap. The cap is off unless set, and the README says to set it: "Always rely on `--max-iterations` as your primary safety mechanism." ([`plugins/ralph-loop/README.md` L134](https://github.com/anthropics/claude-plugins-official/blob/b8e53f1c05dff3b6d751297f6527990ffc81c2f4/plugins/ralph-loop/README.md?plain=1#L134)). Every error path in the hook deletes the state file and lets the session end. *Cost:* one session, no subagents. The only figures are anecdotes with no method given, such as "One $50k contract completed for $297 in API costs" ([`plugins/ralph-loop/README.md` L166-L170](https://github.com/anthropics/claude-plugins-official/blob/b8e53f1c05dff3b6d751297f6527990ffc81c2f4/plugins/ralph-loop/README.md?plain=1#L166-L170)). *Needs:* Claude Code's Stop hook and transcript format, bash, `jq`, `perl`. On Windows: "The stop hook uses a bash script that requires Git for Windows to run properly." ([`plugins/ralph-loop/README.md` L172-L176](https://github.com/anthropics/claude-plugins-official/blob/b8e53f1c05dff3b6d751297f6527990ffc81c2f4/plugins/ralph-loop/README.md?plain=1#L172-L176)), with a workaround that edits a file in the plugin cache.
- **Proposed address**: none.
- **Why it could fit.** It is the smallest loop there is, silent when not in use, and its README is frank about where it does not belong: "Tasks requiring human judgment or design decisions" ([`plugins/ralph-loop/README.md` L159-L164](https://github.com/anthropics/claude-plugins-official/blob/b8e53f1c05dff3b6d751297f6527990ffc81c2f4/plugins/ralph-loop/README.md?plain=1#L159-L164)).
- **Why it might not.** The stop condition is a claim by the model doing the work. A model told never to print a false promise, on a task that cannot be finished, has no way out but the cap. Claude Code's built-in `/goal` does the same job with a separate judge: per its docs, "completion is decided by a fresh model rather than the one doing the work", it clears itself when that model judges the condition impossible, and it reports turns and token spend. `jq` is not on the owner's machine.
- **Copy / adapt / idea-only**: idea-only.
- **Overlap**: the harness `/goal` and `/loop`; A2, A12; [marketplace ledger](ledgers/anthropic-marketplace-plugins.md) entry 18.
- **Idle context cost**: about 55 tokens for its three commands (marketplace ledger).
- **Recommendation (proposed)**: reject, confirming the ledger. Superseded on the owner's harnesses.

### D2. Concurrency caps

- **What it is.** The numbers and bans in the sources.
  - **compound-engineering**: "Cap concurrency at a bounded batch (~3-5 workers), even when more units appear independent." ([`skills/ce-work/references/execution-strategy.md` L22](https://github.com/EveryInc/compound-engineering-plugin/blob/51aa537383744736eb8ad30468d34420e9fb8ea8/skills/ce-work/references/execution-strategy.md?plain=1#L22)). A rolling window beats batches because a batch waits for its slowest member. The cap is on what the coordinator can read, not on machine load; for local work the guide says "Worktrees cost disk and machine resources, so a laptop runs only a handful at once." ([`docs/guide/02-poteto-mode.md` L107](https://github.com/cursor/plugins/blob/ccb5507cec1546dc88135c1139c811e6c59115ba/pstack/docs/guide/02-poteto-mode.md?plain=1#L107)).
  - **superpowers**: no parallel implementers at all (A10). Parallel dispatch is for independent problems only, and a worker never spawns a worker or a reviewer ([`skills/subagent-driven-development/SKILL.md` L272-L277](https://github.com/obra/superpowers/blob/8ca22dba9a94f28898bbce59f2537ff4d87c747d/skills/subagent-driven-development/SKILL.md?plain=1#L272-L277)).
  - **Addy**: fan-out only for independent read-only reviewers, with orchestration depth of one. Its claim that Claude Code forbids nested subagents is out of date: the current docs allow nesting "up to three layers below the main conversation" by default.
  - **The harnesses**: Codex has a setting that caps open spawned-agent threads per session (`agents.max_concurrent_threads_per_session`, vendor docs). Claude Code's bundled `/batch` splits a change into 5 to 30 units, one background subagent and worktree each (vendor docs). No Claude Code or OpenCode setting for a subagent cap was found in the pages read.
- **Kind**: convention.
- **Proposed address**: one sentence in `delegating`; the number itself in harness configuration.
- **Why it could fit.** For Unity work the binding limit is not tokens but the editor: one project lock and one Library folder per checkout, which the planning theme already wrote into `to-tickets` as a surface only one worker can hold at a time (inference for the Unity mapping). The sources' reasons for a cap are all practical: the reader's capacity, cold-start cost per worker, and merge contention.
- **Why it might not.** The owner already keeps a standing limit on parallel agents. A number in a skill is a preference. `implement-spec` is written for "maximum concurrency", so a cap there is a change to a fork skill.
- **Copy / adapt / idea-only**: adapt one sentence: *run parallel workers as a rolling window no wider than you can check, and prefer fewer, broader workers.*
- **Overlap**: `delegating`; fork `implement-spec`, `to-tickets`; [workflow chains](workflow-chains.md) P11.
- **Idle context cost**: none.
- **Recommendation (proposed)**: offer the sentence; set the hard cap where the harness has one (Codex), and leave it to the owner's standing rule elsewhere.

### D3. Dispatching work to another harness

- **What it is.** Three sources send work to another vendor's agent, each by building its own plumbing.
  - **compound-engineering's cross-model engine** is the full version. `ce-work` sends one implementation unit at a time to one of six targets (`codex`, `claude`, `grok`, `cursor`, `composer`, `opencode`) in a detached worktree: "The worker receives one unit, one workspace, one fixed recipient, and only inherited authority." ([`skills/ce-work/references/cross-model-execution.md` L97](https://github.com/EveryInc/compound-engineering-plugin/blob/51aa537383744736eb8ad30468d34420e9fb8ea8/skills/ce-work/references/cross-model-execution.md?plain=1#L97)). The worker leaves its tree uncommitted; the host snapshots it, re-runs the verification itself and makes the only commit: "Never infer success from detached-process completion alone." ([`skills/ce-work/references/cross-model-execution.md` L120](https://github.com/EveryInc/compound-engineering-plugin/blob/51aa537383744736eb8ad30468d34420e9fb8ea8/skills/ce-work/references/cross-model-execution.md?plain=1#L120)). One fallback to native execution is allowed, once. It is candid about safety: "The worker runs with every permission request approved, as the same OS user." ([`skills/ce-work/references/cross-model-execution.md` L84](https://github.com/EveryInc/compound-engineering-plugin/blob/51aa537383744736eb8ad30468d34420e9fb8ea8/skills/ce-work/references/cross-model-execution.md?plain=1#L84)). An unclear request is never passed along for the other model to scope: "An unclear bare prompt returns to clarification or planning before any work is sent to an external worker" ([`skills/ce-work/references/execution-engines.md` L46](https://github.com/EveryInc/compound-engineering-plugin/blob/51aa537383744736eb8ad30468d34420e9fb8ea8/skills/ce-work/references/execution-engines.md?plain=1#L46)). The machinery is about 39 KB of reference text and 370 KB of Python and shell.
  - **davidondrej's `codex-subagent`** is the minimal version: one `codex exec` call per task with the model, effort and sandbox named, the final message written to a file, the diff reviewed by the caller ([`skills/agent-orchestration/codex-subagent/SKILL.md` L35-L43](https://github.com/davidondrej/skills/blob/7874889bd037d411f6079e38ee8601557c4a8995/skills/agent-orchestration/codex-subagent/SKILL.md?plain=1#L35-L43)). Its rules are the useful part: "Codex sees NOTHING of your conversation." ([`skills/agent-orchestration/codex-subagent/SKILL.md` L49-L58](https://github.com/davidondrej/skills/blob/7874889bd037d411f6079e38ee8601557c4a8995/skills/agent-orchestration/codex-subagent/SKILL.md?plain=1#L49-L58)), "One git worktree per Codex run" ([`skills/agent-orchestration/codex-subagent/SKILL.md` L75-L83](https://github.com/davidondrej/skills/blob/7874889bd037d411f6079e38ee8601557c4a8995/skills/agent-orchestration/codex-subagent/SKILL.md?plain=1#L75-L83)), and on a rate limit, "report to the user; never retry in a loop" ([`skills/agent-orchestration/codex-subagent/SKILL.md` L87-L93](https://github.com/davidondrej/skills/blob/7874889bd037d411f6079e38ee8601557c4a8995/skills/agent-orchestration/codex-subagent/SKILL.md?plain=1#L87-L93)).
  - **gstack's `autoplan`** calls `codex exec` for review only, read-only, with a timeout and a parser that treats a refusal or malformed output as missing coverage (A8).
  - **pstack** stays inside Cursor and varies the model family per subagent; its second opinion is "the same prompt against a different model" ([`skills/poteto-mode/SKILL.md` L97](https://github.com/cursor/plugins/blob/ccb5507cec1546dc88135c1139c811e6c59115ba/pstack/skills/poteto-mode/SKILL.md?plain=1#L97)).
  - **superpowers and Addy** dispatch to no other vendor.
- **What T3 Code offers (observed, not documented).** In the session that wrote this file, T3 Code exposed a delegation tool that starts a child agent on a chosen provider and model with only the task prompt, takes a role, a runtime mode and model options such as reasoning effort, runs asynchronously, and wakes the parent with the result. Its provider list reported Codex, Claude, OpenCode and GitHub Copilot as able to run child tasks across providers on this machine, with Cursor, Grok, Pi and two others listed but disabled. A separate tool starts a top-level thread in a new worktree from a named base, and a batch tool takes up to 20 threads. No concurrency cap for delegated children was visible. *Inference:* this covers what the cross-model engine and `codex-subagent` build by hand, including the worktree, on Windows.
- **Kind**: convention.
- **Proposed address**: one sentence in `delegating`; no script and no skill of its own.
- **Why it could fit.** The owner uses T3 Code and wants this for work heavy in parallel agents. The sources' rules for crossing a harness are the same rules `delegating` already holds, made stricter: the brief must stand alone because the worker sees nothing else; one unit per dispatch; the host checks the real tree and owns the commit; a failed dispatch is reported and never retried in a loop. A different model family is also the only form of second opinion pstack and gstack trust, which matters to the review theme.
- **Why it might not.** A skill that names T3 Code is tied to one tool; the collection supports harnesses run without it. A worker on another harness does not load the collection's skills unless that harness also has them installed (it does on this machine for Codex and OpenCode, by the install decision). Permissions differ per harness, and compound-engineering's own text concedes its workers are not confined. How T3 Code children behave under the owner's guard and permission settings was not tested.
- **Copy / adapt / idea-only**: adapt one sentence: *where the harness offers a way to hand a task to a different model or harness, the same brief and the same checks apply, and the brief must stand alone.* The rest is T3 Code's job.
- **Overlap**: `delegating`; [Theme: review and second opinions](https://github.com/Hissal/skill-collection/issues/36) (cross-model review candidates); [davidondrej ledger](ledgers/davidondrej-skills.md) entries 12, 13; [workflow chains](workflow-chains.md) X6.
- **Idle context cost**: none.
- **Recommendation (proposed)**: offer the sentence. Build no dispatch plumbing. A short trial is named under S2. Whether tier and dispatch rules deserve their own pack is a question for a ticket of its own, not for this theme.

## Candidate shapes for this collection

Each is small enough to test by hand on one piece of real work. All three are user-invoked, call `delegating`, keep their state on a ticket, and end before anything is pushed. None needs a script or a hook. If the in-progress pack ticket creates such a pack, all three would start there.

### S1. Goal contract

- **What it is.** A skill that turns one ticket, or one stated outcome, into a four-part contract and hands back the line to type for the harness's own `/goal`. It runs nothing itself. The contract is `delegating`'s brief shape: objective, constraints, validation command, verifiable stop condition. To that it adds a bound (a turn or time clause, which Claude Code's docs suggest writing into the condition), the rule against weakening tests, the discard rule from A2, and an instruction to record each reversible choice on the ticket.
- **Kind**: skill.
- **Proposed address**: core user-invoked, 0 idle tokens.
- **Why it could fit.** It is the one family that is different in kind from the baseline, and it costs almost nothing to try because the loop is the harness's. It respects the #15 rule exactly as the core guide does. It gives `to-tickets`' Proof note a consumer: a ticket whose proof is a command is a ticket this can run.
- **Why it might not.** It may be too thin to deserve a name: a paragraph in `implement` could say the same. It serves only work a command can prove. OpenCode's support for a goal command was not verified.
- **Copy / adapt / idea-only**: adapt from A12 and A2.
- **Overlap**: `delegating`; fork `implement`, `to-tickets`; the harness `/goal`.
- **Idle context cost**: 0.
- **How to test it.** One mechanical ticket with an exact command (a rename across a C# library with its tests, or a coverage lift). Run it once on Claude Code and once on Codex. Record turns and tokens (Claude Code's goal status shows both), whether the stop condition was met honestly, whether any test was weakened, and whether the choices reached the ticket. Compare with one attended `/implement` of a similar ticket.
- **Recommendation (proposed)**: test first.

### S2. Unattended run of a spec

- **What it is.** `implement-spec`'s job with nobody watching: the same tickets, frontier, worktrees and integration branch, with the questions replaced by a written policy taken from A10, A13 and A9. The policy: decide what `git revert` can undo and record it as a ruling (what, why, what it costs if wrong) on the ticket; stop only for the unattended rule's cases; cap fix attempts per ticket and park what remains with a ruling; one review at the end and one fix pass; the orchestrator never edits code; end at the integration branch, unpushed, with a final report that lists every ruling and every unapplied finding. Because a skill takes no behaviour switches, this is a skill of its own beside `implement-spec`, not a mode of it.
- **Kind**: skill.
- **Proposed address**: core user-invoked, or the in-progress pack while under test.
- **Why it could fit.** The owner already runs AFK work, and the fork's thinnest spot for it was named in the earlier report. Everything it needs is decided: tickets as state, `delegating`'s return shape and unattended rule, the Proof note. It adds about a dozen sentences. It is where D1's tier sentences and D3's dispatch sentence would first be exercised.
- **Why it might not.** It overlaps `implement-spec` almost wholly, and the same sentences could go into `implement-spec` itself if the owner accepts that it always runs this way. Rulings on plan defects hand the agent real authority. Whether a pilot ticket (A5) is worth its delay on a five-ticket spec is doubtful.
- **Copy / adapt / idea-only**: write new, from ideas.
- **Overlap**: fork `implement-spec`; `delegating`; A10; [workflow chains](workflow-chains.md) P12, P13, R7, R8.
- **Idle context cost**: 0.
- **How to test it.** One small spec of three to five tickets. Read the rulings list and count how many the owner would have decided differently; that count is the result. Use `session-report` for tokens against an attended `implement-spec` run. As a second trial, have one ticket's implementer dispatched to another harness through T3 Code and check what the brief had to contain.
- **Recommendation (proposed)**: test second.

### S3. Frame, then loop

- **What it is.** The `figure-it-out` shape rewritten harness-neutral: from a stated goal, with no spec. The agent writes a frame (a falsifiable finish condition, a rough size, what it will not touch, the riskiest unknown), builds the check first and captures a baseline, plays the frame back once for a yes, then works in units that are each kept or reverted against the check, with verdicts of verified, not verified or inconclusive. One tracker issue holds the frame and a line per unit. It stops at the finish condition, at a bound agreed in the playback, or at a dead end it writes up.
- **Kind**: skill.
- **Proposed address**: user-invoked; the in-progress pack if one exists, since this is the least proven.
- **Why it could fit.** It is the nearest match to what the owner asked to look at: building big with less planning up front. It keeps one human stop, the playback that `to-spec` already has, and takes its decision classes for that stop from A8.
- **Why it might not.** It competes with `wayfinder` for the same loose, large ideas, and the two should not both claim them. Its safety rests on the check being buildable first, which is often untrue for game feel and visual work. It is the most expensive of the three to get wrong.
- **Copy / adapt / idea-only**: write new, from A3.
- **Overlap**: fork `wayfinder`, `to-spec`, `prototype`; S1 (its loop is S1's loop).
- **Idle context cost**: 0.
- **How to test it.** One bounded migration or port in a C# library where a baseline can be captured. Judge it on two things: was the frame right at the playback, and did the trail on the issue let the owner audit the run without reading the transcript.
- **Recommendation (proposed)**: test last, and only if S1 shows the loop behaves.
