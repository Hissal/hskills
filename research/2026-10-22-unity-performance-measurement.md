# Unity performance measurement beyond ad hoc timers

Bounded primary-source research for wayfinder Unity pack planning, inspected 2026-10-22. API details below use Unity 6.0 documentation and Performance testing API **3.2.1** (`@3.2`); Profile Analyzer documentation resolves to **1.2.4**. These are inspected versions, not a compatibility guarantee for an unspecified project.

## What the methods can answer

- **“Is this synchronous operation cheaper under controlled inputs?” — `Measure.Method`.** Supports warmup, multiple measurements, multiple executions per measurement, and setup/cleanup outside the timed region. Defaults: warmup for at least 100 ms and three executions; nine measurements; automatically selected iteration count targeting approximately 100 ms. Explicit `WarmupCount`, `MeasurementCount`, and `IterationsPerMeasurement` make the workload policy visible. `GC()` counts allocation calls, not allocated bytes or collection pauses. This is useful benchmark machinery beyond one timer reading. [Method measurement](https://docs.unity3d.com/Packages/com.unity.test-framework.performance@3.2/manual/measure-method.html).
- **“Did this scene/scenario's frame times change?” — `Measure.Frames`.** Runs across frames, with configurable warmup and sample count. Defaults: at least 80 ms and three rendered warmup frames, then approximately 500 ms of samples. Can capture specified markers and optionally suppress the frame-time metric with `DontRecordFrametime`. Frame measurements are unsupported in Edit Mode tests. A stable scenario is still the caller's responsibility. [Frame measurement](https://docs.unity3d.com/Packages/com.unity.test-framework.performance@3.2/manual/measure-frames.html).
- **“How much marked work occurred per frame?” — `Measure.ProfilerMarkers`.** Scope-based collection samples once per frame and **sums all invocations** of the named marker in that frame. Supports named sample groups and units. Unsupported in Edit Mode, Deep Profiling, and for labels made with `Profiler.BeginSample`; use `ProfilerMarker` where applicable. [Marker measurement](https://docs.unity3d.com/Packages/com.unity.test-framework.performance@3.2/manual/measure-profile-markers.html).
- **“Did another measurable property change?” — `Measure.Custom`.** Records a caller-supplied numeric sample with a sample group/unit; Unity's example records total allocated memory. Candidate metrics include workload counts or domain throughput, but their definition and collection correctness belong to the harness. [Custom measurement](https://docs.unity3d.com/Packages/com.unity.test-framework.performance@3.2/manual/measure-custom.html).
- **“Where does the cost occur in the running workload?” — `ProfilerMarker` plus a capture or recorder.** Named instrumentation works in jobified code and avoids repeatedly transferring marker strings. Its `Begin`/`End` calls are compiled away in non-Development builds. [ProfilerMarker](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Unity.Profiling.ProfilerMarker.html).
- **“Can a harness collect metrics without reading the Profiler UI?” — recorder APIs.** `ProfilerRecorder` exposes marker timings and counters, including memory/render statistics, in Editor and Player, including Release. Enumerate supported metrics with `ProfilerRecorderHandle.GetAvailable`; dispose its unmanaged resources. Release support does **not** mean stripped custom instrumentation survives. Older `UnityEngine.Profiling.Recorder` accumulates a sampler's Begin/End durations for the previous frame, independent of whether the Profiler is recording; validate `isValid`, with samplers limited to Editor/Development Players. [ProfilerRecorder](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Unity.Profiling.ProfilerRecorder.html), [Recorder](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Profiling.Recorder.html).
- **“Did the distribution of frame/marker costs change between captures?” — Profile Analyzer.** Aggregates multiple Profiler frames and compares two data sets side by side. It complements single-frame investigation; it does not standardize the workload or collect independent benchmark trials. Keep the original `.data`/`.raw` capture as well as `.pdata`, which does not contain the original profile. [Profile Analyzer](https://docs.unity3d.com/Packages/com.unity.performance.profile-analyzer@1.2/manual/index.html).
- **“Is the frame limited by CPU, GPU, or presentation?” — `FrameTimingManager`.** Exposes CPU frame, main-thread, render-thread, presentation-wait and GPU times. CPU frame time includes waiting/overhead; GPU time can include idle periods. Read these together rather than treating CPU time as useful CPU work. [FrameTiming definitions](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/FrameTiming.html). Results arrive four frames late; availability varies by platform/API (for example no GPU frame time on WebGL/Linux OpenGL). GPU timing can fail, and tile-based GPUs can report times spanning deferred phases. OpenGL ES collection may itself reduce GPU performance. Release collection requires Frame Timing Stats. [Manager limits](https://docs.unity3d.com/6000.0/Documentation/Manual/frame-timing-manager.html), [getting data](https://docs.unity3d.com/6000.0/Documentation/Manual/frame-timing-manager-get-timing-data.html).

## Repeatability: useful controls, bounded claims

Both method and frame APIs offer `DynamicMeasurementCount`: its documented defaults target **2% relative error of the mean at 99% confidence**, excluding statistical outliers unless configured otherwise. Explicit error/confidence/outlier settings are available. This establishes adaptive sampling, not BenchmarkDotNet equivalence or guaranteed reproducibility across machines/runs. [Method sampling](https://docs.unity3d.com/Packages/com.unity.test-framework.performance@3.2/manual/measure-method.html), [frame sampling](https://docs.unity3d.com/Packages/com.unity.test-framework.performance@3.2/manual/measure-frames.html).

**Experimental implications (inference):** a narrow interval can describe a consistently biased or unrepresentative experiment. Repeated executions in one measurement are not independent application launches. Batches can mutate state, warm caches, reuse allocations, and change branch/data locality. Setup/cleanup can restore logical inputs while warming memory themselves. Define whether the question concerns cold start, steady state, or realistic frame cadence; choose batching/reset policy accordingly. Excluding outliers can hide the stalls relevant to a hitch investigation. Compare distributions and repeat whole scenario runs when run-to-run variation matters, rather than relying on one mean.

The package records build/player configuration metadata and can export JSON through `-perfTestResults`. Those provide useful evidence for comparisons, without controlling workload, device load or thermal state automatically. Record Unity/package versions, backend/Burst configuration, device, scenario/input, quality/resolution, frame cap/VSync, warmup/reset/batch policy and instrumentation settings as the experiment's context. This recording list is a research recommendation. [Package overview](https://docs.unity3d.com/Packages/com.unity.test-framework.performance@3.2/manual/index.html), [results argument](https://docs.unity3d.com/Packages/com.unity.test-framework.performance@3.2/manual/cmd-line-args.html).

## Stopwatch, asynchronous work, and the frame critical path

`Stopwatch` is not inherently a rough timer: it uses a high-resolution performance counter when available; `IsHighResolution` and `Frequency` describe the timer, and ticks avoid whole-millisecond reporting granularity. It measures elapsed wall time, including time spent waiting or descheduled. Clock resolution alone cannot guarantee benchmark accuracy; interval length, measurement overhead and workload variation still matter. [Microsoft Stopwatch documentation](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.stopwatch?view=net-9.0).

**Measurement-boundary implications (inference):** timing a job scheduling call measures scheduling/submission, not necessarily completed work. Timing scheduling through `JobHandle.Complete` includes synchronization/dependencies and can change execution: Unity prioritizes those jobs and may execute work on the calling thread. Thus forced completion can destroy the overlap the production frame relies on. [JobHandle.Complete](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Unity.Jobs.JobHandle.Complete.html). Likewise, a CPU timer around render submission does not establish GPU execution time; use GPU-aware data with its reporting delay and limits above.

**Method duration, summed marker work, and frame critical-path delay answer different questions.** Parallel CPU/GPU work overlaps; reducing total worker time need not shorten the frame, and adding overlapping/nested marker durations does not reconstruct its critical path. Treat microbenchmarks as evidence about the operation, then inspect thread ordering, waits and frame results to establish user-visible impact. This is an inference from the timing boundaries; Unity's CPU Timeline provides the cross-thread view needed to investigate it. [CPU Profiler reference](https://docs.unity3d.com/6000.0/Documentation/Manual/ProfilerCPU.html).

## Player evidence and its cost

Unity recommends target-platform profiling for representative timings. Play mode shares the Editor's process/main thread and competes with inspectors, UI, Scene rendering and asset management, making it useful for fast iteration but insufficient for device claims. Builds/deployment cost time; a practical evidence loop can investigate on device, iterate locally, then rebuild to validate the candidate change. [Collect performance data introduction](https://docs.unity3d.com/6000.0/Documentation/Manual/profiling-collect-data-introduction.html).

**A built performance test is not automatically a release benchmark.** The Performance Testing Package explicitly says Unity Test Framework always builds a Development Player for Editor/Player communication, overriding the UI/API development-build setting. A release-equivalent harness is a separate choice, potentially using available `ProfilerRecorder` metrics/custom timing or Frame Timing Stats. [Package caveat](https://docs.unity3d.com/Packages/com.unity.test-framework.performance@3.2/manual/index.html). Deep Profiling support inserts checks around every C# method and can significantly slow the Player even when active Deep Profiling is off; active recording adds more overhead. [Deep Profiling build option](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/BuildOptions.EnableDeepProfilingSupport.html).

**Planning implication:** useful pack coverage is choosing the measurement boundary, controlling the experiment, and stating what the evidence supports. These methods are complementary options; the evidence does not justify prescribing one framework for every performance question. No Editor, benchmark, package installation or Player build was run for this research; measured overhead and attainable repeatability remain project/device-specific unknowns.
